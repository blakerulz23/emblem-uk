## Ordinary builder authority (decision 13) — near-total gap versus Squad Invite

Squad Invite (decision 14) already implements strong, specific authority machinery (`docs/pilot/squad-invite-controlled-pilot-runbook.md`, migrations 0050–0070) — verified consistent with the founder's decisions in the controls-and-tests matrix. **The ordinary direct/team builder (used by decisions labelled "direct one-player builder" and "multi-player builder" in the DPIA's own journey map) does not share any of that machinery.** Traced directly against `ProductionBuilder.tsx`'s review-step form, `order-enquiry-validation.ts`, `order-enquiry/route.ts`, and the `create_authoritative_order` RPC:

| Sub-item | Status | Evidence |
|---|---|---|
| (a) verified parent/adult email | 🔴 Not implemented | Email is regex-format-checked only (`order-enquiry-validation.ts:240`); no OTP/magic-link exists on this path |
| (b) purchaser confirms 18+ | 🔴 Not implemented | No such field exists anywhere in the form state or server validation |
| (c) purchaser confirms parental responsibility/authority | 🔴 Not implemented | No such field exists |
| (d) separate agreements for photo use / manufacture / profile | 🔴 Not implemented | The entire review step has only Name, Email, Phone, Notes — **zero checkboxes of any kind**, not even one bundled checkbox |
| (e) non-parent purchaser needs guardian-email approval | 🔴 Not implemented | `orders.intended_guardian_email` column exists but is never populated by this flow — it's used post-approval as an invite recipient, not a pre-finalisation gate |
| (f) coach status alone is insufficient | 🔴 Not implemented | No authority concept exists at all on this path to check "insufficiency" against |
| (g) every pilot order gets manual staff review | 🟢 Implemented | Generic payment/production staff gate (`staff/queue`, `POST /api/orders/[id]/approve`) — but this is a payment/fulfilment gate that predates and is not itself a consent/authority review |
| (h) disputed authority freezes processing | 🔴 Not implemented | No dispute/freeze concept exists on the `orders` table; the closest analogue (`organiser_flagged_concern`) is Squad-Invite-only |
| (i) consent wording version, timestamp, evidence recorded | 🔴 Not implemented | No columns exist to record this, consistent with (a)-(d) not existing to record |

**This is the second-highest-priority engineering gap in this pass.** Every real order placed through the ordinary builder today proceeds with materially less authority verification than Squad Invite's already-built flow, and with none of what decision #13 just specified. If the pilot's real orders are expected to go through the ordinary builder rather than exclusively through Squad Invite, this must be closed before real use; if the pilot is Squad-Invite-only in practice, this should be stated explicitly as a scope decision, not left implicit.
